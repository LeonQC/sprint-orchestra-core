## Overview

- **19 tables, 168 columns** in the `public` schema. `flyway_schema_history` is Flyway's own
  table and is not listed.
- The schema is changed only through Flyway migrations; JPA runs with `ddl-auto: validate`.
- Full-text search is not in PostgreSQL. Issues and comments are indexed in OpenSearch, which is
  rebuilt from these tables (see [ARCHITECTURE.md](ARCHITECTURE.md)).
- The "Current definition" blocks below show each table as it is after all migrations, not the
  migration steps.

Migrations by area:

| Migrations | What they do |
| --- | --- |
| V1–V6 | Users, spaces, groups, sprints, issues, comments, history, links, attachments, GitHub code links and repos |
| V7–V11, V13 | Attachment panel visibility, per-space GitHub token, code-link activity time, space soft delete, Google and GitHub account ids |
| V12, V14 | Demo user data only |
| V15–V17 | Drop work logs, sprint ordering, remove type-like labels |
| V18–V22 | Space label catalog, sprint issue history and sprint metrics, plus data backfills |
| V23–V29 | PostgreSQL full-text and trigram search (all removed again by V30) |
| V30 | Drop every full-text artifact; search runs in OpenSearch |
| V27 | Idempotency keys |
| V31–V32 | AI feedback |
| V33–V34 | Two-level comment replies |
| V35–V36 | bcrypt password hashes and demo users |

### Table: users

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| id | BIGINT | PK, identity | User id |
| username | VARCHAR(50) | UNIQUE, NOT NULL | Login username |
| name | VARCHAR(100) | NOT NULL | Display name |
| email | VARCHAR(150) | UNIQUE, NOT NULL | User email |
| password | VARCHAR(100) | NULL | bcrypt hash (`$2a$`, V35); NULL when the account has no password |
| avatar_color | VARCHAR(100) | NULL | UI avatar color |
| created_at | TIMESTAMPTZ(6) | NOT NULL | Created time |
| updated_at | TIMESTAMPTZ(6) | NOT NULL | Updated time |
| google_sub | VARCHAR(255) | NULL | Legacy Google OAuth subject from V11; retained in PostgreSQL but not mapped by the current `User` entity |
| github_id | VARCHAR(255) | NULL | GitHub account id (V13) |

**Current definition:**

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    username VARCHAR(50) NOT NULL,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL,
    password VARCHAR(100),
    avatar_color VARCHAR(100),
    created_at TIMESTAMPTZ(6) NOT NULL,
    updated_at TIMESTAMPTZ(6) NOT NULL,
    google_sub VARCHAR(255),
    github_id VARCHAR(255),
    CONSTRAINT uk_users_email UNIQUE (email),
    CONSTRAINT uk_users_username UNIQUE (username),
    CONSTRAINT users_pkey PRIMARY KEY (id)
);

CREATE UNIQUE INDEX uk_users_github_id ON users (github_id) WHERE (github_id IS NOT NULL);
CREATE UNIQUE INDEX uk_users_google_sub ON users (google_sub) WHERE (google_sub IS NOT NULL);
```

### Table: labels

Space-scoped label catalog introduced in **V18**. Replaces the legacy string-valued `issue_labels` table. Labels are case-insensitive via `normalized_name`; the first spelling used in a space is preserved in `name`.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| id | BIGINT | PK, identity | Label id |
| space_id | BIGINT | FK -> spaces(id), NOT NULL | Owning space |
| name | VARCHAR(50) | NOT NULL | Display spelling |
| normalized_name | VARCHAR(50) | NOT NULL | Case-insensitive key; internal whitespace collapsed (V21) |
| created_at | TIMESTAMPTZ(6) | NOT NULL | Created time |
| deleted_at | TIMESTAMPTZ(6) | NULL | Soft-delete timestamp |

Reserved normalized names (`bug`, `story`, `epic`) belong in `issues.issue_type` and must not be created as labels. The internal `flagged` label is filtered from list APIs.

**Current definition:**

```sql
CREATE TABLE labels (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    space_id BIGINT NOT NULL,
    name VARCHAR(50) NOT NULL,
    normalized_name VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ(6) NOT NULL,
    deleted_at TIMESTAMPTZ(6),
    CONSTRAINT uk_labels_space_normalized UNIQUE (space_id, normalized_name),
    CONSTRAINT labels_pkey PRIMARY KEY (id),
    CONSTRAINT fk_labels_space FOREIGN KEY (space_id) REFERENCES spaces(id)
);

CREATE INDEX idx_labels_space_active ON labels (space_id, deleted_at);
```

### Table: comments

Comments on an issue, in two-level threads (**V33**, **V34**): a reply always points at the top-level comment of its thread through `parent_id`, and `reply_to_id` keeps which comment it actually answered.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| id | BIGINT | PK, identity | Comment id |
| issue_id | BIGINT | FK -> issues(id), NOT NULL | Issue id |
| author_id | BIGINT | FK -> users(id), NOT NULL | Author user id |
| content | TEXT | NOT NULL | Comment content |
| created_at | TIMESTAMPTZ(6) | NOT NULL | Created time |
| updated_at | TIMESTAMPTZ(6) | NOT NULL | Updated time |
| parent_id | BIGINT | FK -> comments(id), NULL | Top-level comment this reply belongs to; NULL for a top-level comment (V33) |
| reply_to_id | BIGINT | FK -> comments(id), NULL | Comment this reply answered; set to NULL if that comment is deleted (V34) |

**Current definition:**

```sql
CREATE TABLE comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    issue_id BIGINT NOT NULL,
    author_id BIGINT NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ(6) NOT NULL,
    updated_at TIMESTAMPTZ(6) NOT NULL,
    parent_id BIGINT,
    reply_to_id BIGINT,
    CONSTRAINT comments_pkey PRIMARY KEY (id),
    CONSTRAINT fk_comments_author FOREIGN KEY (author_id) REFERENCES users(id),
    CONSTRAINT fk_comments_issue FOREIGN KEY (issue_id) REFERENCES issues(id),
    CONSTRAINT fk_comments_parent FOREIGN KEY (parent_id) REFERENCES comments(id),
```

## Key Relationships

### Relationship 1: Space-centered hierarchy

- `spaces` -> `sprints` (1:N)
- `spaces` -> `issues` (1:N)
- `spaces` -> `labels` (1:N)
- `issues` -> `comments` / `issue_history` / `issue_attachments` / `issue_code_links` (1:N)
- `sprints` -> `sprint_issue_history` (1:N)

### Relationship 2: Membership model

- `spaces` <-> `users` via `space_members`
- `user_groups` <-> `users` via `group_members`
- `spaces` <-> `user_groups` via `space_groups`

This supports both direct and group-based membership.

### Relationship 3: Issue graph and labeling

- `issues.parent_id` supports parent-subtask hierarchy
- `issue_links` supports typed links across issues
- `issues` <-> `labels` via `issue_labels`

### Relationship 4: Comment threads

- `comments.parent_id` -> `comments` (a reply's top-level comment; threads are two levels deep)
- `comments.reply_to_id` -> `comments` (the comment a reply answered)

### Relationship 5: Dev integration

- `space_github_repos` defines the repos connected to a space
- `issue_code_links` stores issue-level links to PRs, commits, branches and repos
- `spaces.github_pat` enables private-repo access per space

### Relationship 6: AI feedback

- `ai_feedback.reporter_id` and `ai_feedback.reviewer_id` -> `users`
- `ai_feedback.answer_id` refers to an ai-service answer, not to a table; `(answer_id, reporter_id)` is unique

## Notes on Implementation

1. **Schema ownership**
   - Managed by Flyway migrations `V1`..`V36`; JPA validates against it (`ddl-auto: validate`)

2. **Issue identifiers**
   - `issues.id` is the relational primary key
   - `issues.issue_key` is the unique business key shown in the UI and API

3. **Rich content**
   - `issues.description` and `comments.content` are `TEXT` and may contain HTML from the editor

4. **Attachments**
   - Files live in S3-compatible storage under `storage_filename`
   - `list_in_attachment_panel` hides attachments that are only embedded in rich text
   - Deleting an attachment does not edit HTML that mentions it (application responsibility)

5. **Passwords**
   - `users.password` holds a bcrypt hash; the application never stores or compares plain text

6. **Search**
   - PostgreSQL holds no full-text or trigram index. jira-backend writes issue and comment documents
     to OpenSearch after each commit, and `GET /api/search` queries OpenSearch
   - The `pg_trgm` extension created by V26 stays installed but is unused

7. **Idempotent writes**
   - `idempotency_keys` stores the first response to a write that carried an `Idempotency-Key`
     header; a retry with the same key gets that response back

8. **Deletion behavior**
   - Most foreign keys use the default (restrict if referenced); deletes are orchestrated by the
     service layer. `comments.reply_to_id` is the exception: `ON DELETE SET NULL`
   - `spaces` and `labels` use soft delete via `deleted_at`

9. **Sprint reporting**
   - Completed sprint metrics on `sprints` are derived from `sprint_issue_history`
   - Point totals may be `NULL` when history would be misleading

## Other schemas in the same database

The same PostgreSQL database holds two more schemas, owned by the AI services rather than by
Flyway. Neither has foreign keys into `public`.

| Schema | Owner | Tables |
| --- | --- | --- |
| `rag` | vectorization-service ([rag_schema.sql](../vectorization-service/schema/rag_schema.sql)) | `chunks`, `chunk_parents`, `ingestion_status`, `vlm_result_cache`, `vlm_retry_queue` |

`rag.chunks.embedding` is a pgvector column with an HNSW cosine index. Kafka delete events keep
the `rag` tables in step with business rows. Exact counts and history are always read from the

business tables.
